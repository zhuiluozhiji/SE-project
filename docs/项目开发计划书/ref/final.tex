\chapter{引言}

\section{编写目的}

本文档旨在详细描述“校园学术活动智能推荐平台”的需求边界、核心功能与质量标准，为后续系统设计、开发实现、测试验收与课程答辩提供统一依据。具体目标如下：

\begin{enumerate}[leftmargin=2.5em]
\item 统一项目干系人（学生、教师、管理员、开发成员）对系统目标与范围的理解。
\item 将用户需求转换为可落地、可验证的功能与非功能需求。
\item 为后续概要设计、数据库设计、接口设计提供输入。
\item 为测试用例编写与阶段验收提供可量化标准。
\end{enumerate}

\section{项目背景}

浙江大学学术讲座、论坛、Workshop、学术沙龙等活动资源丰富，信息来源覆盖浙江大学官网、求是新闻网、研究生院/本科生院通知、各学院与研究机构官网，以及“浙江大学”等官方微信公众号和学院官号。以计算机科学与技术学院为例，活动通知往往分别发布在各自网站或公众号中，发布时间、字段格式和报名入口并不完全统一。

这种多来源发布方式保证了学院和部门的自主性，但对普通学生和教师来说，也带来了“渠道多、更新快、组织散”的典型问题。用户如果想持续关注人工智能、数字人文、生命科学、创新创业等不同方向的活动，通常需要反复浏览多个官网栏目、公众号推文和校内通知群，信息检索成本较高。师生在获取信息时常面临如下痛点：

\begin{enumerate}[leftmargin=2.5em]
\item 信息接收滞后：活动可能先发布在学院官网或公众号中，用户未及时关注时容易错过报名窗口或关键讲座。
\item 个人相关性低：浙江大学学科门类多、活动数量大，用户需要从大量通知中筛选与个人专业、研究方向或兴趣匹配的内容。
\item 时间安排困难：讲座、课程、实验、组会和考试安排可能发生冲突，用户需要手动判断是否适合参加。
\item 跨校区成本高：紫金港、玉泉、西溪、华家池等校区之间存在通勤成本，用户缺少活动地点与出发时间的综合提醒。
\end{enumerate}

本项目旨在面向浙江大学师生建设一个集“信息采集、智能推荐、日程协同、社交互动”于一体的平台，对接和整理浙江大学官网、求是新闻网、学院官网、官方微信公众号等公开活动信息，通过算法与业务规则结合，帮助用户高效发现并参与高价值学术活动。

\chapter{总体描述}

\section{产品前景}

该平台定位为浙江大学学术活动的“统一入口 + 智能日程助手”，以提升活动触达效率与参与质量为核心价值。平台前期重点聚合浙江大学官网、求是新闻网、研究生院/本科生院通知、各学院官网和官方微信公众号中的公开活动信息，统一抽取活动标题、时间、地点、主讲人、报名方式、所属学院和主题标签等字段，形成面向师生的集中式活动信息流。

在使用场景上，平台不仅解决“在哪里看到活动”的问题，还进一步解决“是否值得参加、是否和课表冲突、跨校区是否来得及”的问题。例如，用户可以在同一界面查看紫金港校区的人工智能讲座、玉泉校区的工程技术论坛、西溪校区的人文社科沙龙和华家池校区的生命科学活动，并根据个人兴趣标签、课程表和通勤时间获得推荐与提醒。

在课程项目阶段，平台优先实现可展示、可交互、可验收的核心闭环，包括活动聚合展示、标签筛选、个性化推荐模拟、加入日程、冲突提示和 ICS 导出。在后续迭代中，再逐步接入真实数据源、统一身份认证、学院活动发布后台和更完整的多校区通勤服务。

阶段性愿景如下：

\begin{enumerate}[leftmargin=2.5em]
\item 第一阶段：基于浙江大学公开活动信息样例，实现活动聚合、检索、推荐、加入日程与日历同步闭环。
\item 第二阶段：接入学院或社团活动发布入口，加强学术组队、笔记、评价与运营后台能力。
\item 第三阶段：接入统一身份认证、课表数据和地图/路径规划服务，支持更精准的个性化推荐、冲突检测和跨校区通勤提醒。
\end{enumerate}

\section{运行环境}

\subsection{客户端环境}

\begin{enumerate}[leftmargin=2.5em]
\item Web 端：Chrome、Edge、Safari 主流版本。
\item 移动端：微信小程序或 H5（兼容 Android/iOS 主流机型）。
\end{enumerate}

\subsection{服务端环境}

\begin{enumerate}[leftmargin=2.5em]
\item 操作系统：Linux（Ubuntu/CentOS）或 Windows Server（开发测试阶段可选）。
\item 运行框架：Python/Java 等主流后端框架之一（按团队技术栈落地）。
\item 数据存储：MySQL/PostgreSQL + Redis。
\item 异步任务：Celery 或同类队列框架。
\end{enumerate}

\subsection{外部依赖}

\begin{enumerate}[leftmargin=2.5em]
\item 学校统一身份认证（SSO/CAS）。
\item 地图/路径规划 API（用于跨校区通勤估算）。
\item 第三方日历 API（Google/Outlook 等，可选）。
\end{enumerate}

\section{设计和实现上的约束}

\begin{enumerate}[leftmargin=2.5em]
\item 合规约束：仅抓取公开信息，遵守目标网站 robots 与学校数据管理规范。
\item 安全约束：必须接入统一认证并实施接口限流、防刷与审计日志。
\item 性能约束：推荐接口与关键页面响应需满足第5章性能目标。
\item 资源约束：课程项目周期有限，优先实现核心闭环功能。
\item 可维护约束：爬虫、推荐、业务流程应模块化解耦，便于独立迭代。
\end{enumerate}

\chapter{系统功能}

当前校园师生在获取学术活动信息时面临渠道分散、信息过载的问题，且难以将其与个人繁杂的课表和日程有效结合。用户迫切需要一个统一的信息聚合平台，能够根据自身的学科背景和兴趣自动推荐高质量讲座，并提供一键排程、冲突预警及跨校区通勤规划等智能化服务，从而降低时间管理成本，提升学术交流效率。基于对平台使用对象（学生、教师、组织者、系统管理员）的特征分析，具体用户需求如下：

\chapter{非功能性需求}

系统不仅需要满足业务上的各项具体功能，其内部的运行质量、系统健壮性以及用户交互体验也至关重要。

\section{性能需求}

系统的性能表现直接影响师生的使用体验。

为了保证流畅的交互，

\begin{itemize}[leftmargin=2.5em]
\item 前端页面（含 Web 端和微信小程序）的首屏加载时间应当被严格控制在 2 秒以内。
\item 在操作日历视图时，涉及大量数据的渲染与月份切换，其响应延迟需要保持在 1 秒以内。
\item 个性化推荐接口的响应时间不得超过 500 毫秒。
\end{itemize}

在并发处理方面，考虑到开学季或者有重要知名学者开展讲座等访问量激增的场景，

\begin{itemize}[leftmargin=2.5em]
\item 后端服务架构必须具备足够的健壮性，能够稳定承载至少 500 QPS 的并发访问，以确保系统在流量高峰期不会出现宕机或拒绝服务的情况。
\end{itemize}

\section{输入要求}

在数据源及用户上传的文件兼容性层面，由于需要从多个院系官网或外部渠道获取活动信息，

\begin{itemize}[leftmargin=2.5em]
\item 系统必须具备良好的文本容错与解析能力，能够自适应并解析多种非标准格式的外部网页源码及复杂的 JSON 数据流。
\end{itemize}

为了方便学生导入各自的学期课程表，

\begin{itemize}[leftmargin=2.5em]
\item 系统既需要支持提取主流图片格式的课表进行 OCR 智能识别输入，也应该允许用户通过 Excel 或 CSV 等结构化格式直接提取、转化、汇入。
\end{itemize}

\section{数据传输及并发要求}

针对后台可能出现的高压工作流和实时通信场景，系统在数据传输与并发机制上做了特定要求。

对于底层的数据爬取、大量的批量告警或邮件发送模块，以及计算资源消耗密集的推荐算法任务，

\begin{itemize}[leftmargin=2.5em]
\item 应当采取异步削峰的策略，统一交由如 Celery 这样的异步任务队列引擎调度执行，以此避免耗时操作阻塞系统的主服务响应线程。
\end{itemize}

同时，在学术活动组队、用户点对点社交互动等实时场景中，

\begin{itemize}[leftmargin=2.5em]
\item 后端系统还要提供 WebSocket 协议下的长稳定连接支持，以满足消息即时双向推送和渲染更新的需要。
\end{itemize}

\section{数据管理需求}

面对高频产出的全校学术数据与师生画像档案，系统的数据管理必须兼顾安全与长期检索效率。

为了实现平台的高可用性，

\begin{itemize}[leftmargin=2.5em]
\item 核心关键数据库需配置主备从同步策略，并严格落实每日冷备份机制，将整体的数据层可用性提升并稳定在 99.9\%，杜绝单点物理故障带来的数据丢失或损坏风险。
\end{itemize}

在此基础上，由于讲座及活动数据具有明显的时效性，

\begin{itemize}[leftmargin=2.5em]
\item 系统还需引入数据归档机制，每隔一个学年定期将系统中超过一年的历史讲座数据进行分表甚至异地长效归档存储，从而剥离无效数据并大幅度减轻主数据表线上查询压力。
\end{itemize}

\section{权限与安全需求}

平台的数据安全与越权风险拦截是保障良好学术环境的关键。

作为一款主要面向校内用户的产品，

\begin{itemize}[leftmargin=2.5em]
\item 系统要求与浙江大学校内现有的统一身份认证平台（SSO/CAS 等）进行深度集成，依靠校方级安全认证鉴权，确保校内讲座信息与社交活动等核心资源仅限本校师生登录访问。
\end{itemize}

在防止恶意爬取方面，

\begin{itemize}[leftmargin=2.5em]
\item 任何暴露给前段的 API 接口均需要配置严格的速率限制与反爬防火墙，借以防止恶意脚本或爬虫批量抓取整合后的高价值结构化数据池，有效抵挡由于频繁请求而造成的 DDoS 渗透攻击或服务瘫痪。
\end{itemize}

\section{软件质量属性}

在追求功能完善的同时，平台系统架构设计同样应着眼于长远的迭代成本。

\begin{itemize}[leftmargin=2.5em]
\item 后端的代码架构应深入贯彻高内聚、低耦合的设计哲学，刻意将最容易变动和受阻的分布式爬虫组件模块、计算属性导向的推荐引擎模型，同平台基础的用户和核心业务流做到服务解耦式拆分，如此可以保障各大系统的后续代码扩展具有极为优异的可维护特质。
\end{itemize}

\begin{itemize}[leftmargin=2.5em]
\item 与此同时，所有服务端组件、脚本服务与依赖环境都应要求支持基于 Docker 等容器技术的标准化打包，便利后续工程平台横向平推与云服务器集群上的多实例无缝扩缩容调配。
\end{itemize}

\section{可视化需求}

平台不仅需要健壮的底层，也应提供优质、友善且富有包容性的操作界面。

\begin{itemize}[leftmargin=2.5em]
\item 前端页面的视觉交互需建立在完善的响应式适配方案之上，保证兼顾移动端用户高频操作习惯与手势滑动的同时，在平板、PC 宽屏环境下的多活动视窗下体验也不打折扣。
\item 平台标志性的核心日历控件必须直观清晰，应针对活动不同的时间冲突态、路程通勤态及完全可行态规划截然不同的状态色块与直观 ICON。
\item 另外，无障碍设计的考量应当被放在界面的初始设计阶段——控件面板交互组件都应当契合人体工程学尺寸，并且界面的高明度设计保障用户哪怕身处学生户外强光环境依然能够顺畅读取系统关键提示与文本内容。
\end{itemize}

\section{防护性需求}

平台高度依赖外部数据整合及展示服务，故建立起自有的容错、降级及自动侦测恢复屏障更是重中之重。

系统需要考虑到对地图评估 API 服务器或校内教务系统课表接口等外联调用时可能产生的超时、假死甚至全线宕机情况，当外界因素波动干扰不可逆转时，平台要具备无缝切换的柔性兜底预案（如暂时切换至配置好的全校默认地理时间差常量等），坚决确保本系统内核心日历基础运转不受拖累连带影响。而针对极不稳定且环境抗变弱的源站信息爬虫提取端，采集网络更是要加入智能自动化自检恢复逻辑。当感知到目标院系网页 HTML 标签存在小幅调整甚至是检测到自身节点短频访问触发 IP 封锁控制时，系统能在最快时间内完成自动化内部预警追踪、挂起重试乃至自动更换轮替高匿代理池执行断点恢复。
